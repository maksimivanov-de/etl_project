# ETL: витрина мошеннических операций

Финальный проект курса «SQL для прикладных задач».

Процесс забирает ежедневную выгрузку, складывает её в хранилище
и строит витрину по мошенническим операциям.

## Настройка на macOS / Linux

Нужны Python 3.12 и запущенный локальный PostgreSQL (проверено на PostgreSQL 18.6).
Пользователь PostgreSQL должен иметь право создавать базы. По умолчанию
используются localhost:5432, имя пользователя ОС и база `etl_project`.
Если сервер требует пароль или другое имя пользователя, заранее скопируйте
`.env.example` в `.env` и заполните параметры. `.env` не попадает в Git.

После клонирования перейдите в папку проекта и выполните:

```bash
./setup.sh
```

Скрипт создаст `.venv`, установит зафиксированные зависимости, создаст `.env`,
если его ещё нет, и отдельную базу `etl_project`. При первой настройке
учебные таблицы и данные из `ddl_dml.sql` загружаются в схему `bank`
в одной транзакции. ETL при настройке не запускается.

Повторная настройка сохраняет `.env` и существующие таблицы источника.
Если источник подготовлен частично, скрипт остановится без перезаписи данных.
Существование всех трёх таблиц считается признаком подготовленного источника;
это не проверка их содержимого и не миграция схемы. Автоматического сброса нет.

Если Python 3.12 установлен под другим именем:

```bash
PYTHON_BIN=/путь/к/python3.12 ./setup.sh
```

Настройки подключения едины для всех этапов:
`DATABASE_HOST`, `DATABASE_PORT`, `DATABASE_NAME`, `DATABASE_USER`,
`DATABASE_PASSWORD`. Переменные окружения имеют приоритет над `.env`.
Установка PostgreSQL, запуск службы и создание роли выполняются отдельно.
Для Homebrew после установки PostgreSQL 18 службу можно запустить командой
`brew services start postgresql@18`.

## Запуск

```bash
.venv/bin/python main.py
```

Входные файлы ищутся в `data/` рядом с `main.py`, независимо от текущей папки.
Обработанные файлы перемещаются в `archive/`. Повторная настройка их не возвращает.
Ограничения восстановления после сбоев описаны ниже.

## Структура

```
main.py                 порядок шагов процесса
py_scripts/ddl.py       создание объектов хранилища и расчёт инкрементов
py_scripts/load.py      загрузка источников в стейджинг
py_scripts/db.py        применение инкрементов, витрина, метаданные
py_scripts/files.py     перенос обработанных файлов в архив
data/                   входные файлы выгрузки
archive/                отработанные файлы, переименованные в .backup
```

## Слои хранилища

```
STG_*                стейджинг, зеркало источника, живёт один прогон
DWH_DIM_*_HIST       измерения в формате SCD2
DWH_FACT_*           факты, только вставка
REP_FRAUD            витрина, строится накоплением по report_dt
META_LOAD            журнал загрузок: какой день обработан и когда
```

Измерения (терминалы, карты, счета, клиенты) версионируются:
у записи есть effective_from, effective_to и deleted_flg,
поэтому можно выбирать версии для периодов, за которые история накоплена.

Инкремент считается сравнением стейджинга с актуальным срезом истории:
отдельно новые записи, пропавшие и изменившиеся.

## Правила витрины

1. Операция при просроченном или заблокированном паспорте
2. Операция при недействующем договоре
3. Операции в разных городах за интервал не более одного часа (ровно 60 минут включаются)
4. Подбор суммы: более трёх операций за 20 минут, каждая меньше
   предыдущей, все отклонены кроме последней

## Соответствие заданию

Условия: [Итоговый проект](https://github.com/HaykInanc/sql_project/blob/master/Итоговый%20проект.pdf).
Реализован усложнённый вариант SCD2. Среда адаптирована с Oracle на PostgreSQL.
Сохраняются имена полей ER-схемы, включая `patrinymic`, и поля REP_FRAUD:
`event_dt`, `passport`, `fio`, `phone`, `event_type`, `report_dt`.
`event_dt` — время операции; `report_dt` — фактическое время вычисления отчёта.
Дата входного пакета хранится в META_LOAD и META_FILES.

## Запуск и поздние транзакции

Без параметров процесс обнаруживает файлы по шаблонам задания в `data/`
и обрабатывает даты по возрастанию. Можно выбрать даты явно:

```bash
.venv/bin/python main.py --date 2021-03-01 --date 2021-03-02
```

Для дополнительного файла операций прошлой даты:

```bash
.venv/bin/python main.py --transactions-only --date 2021-03-01
```

Файл должен называться `data/transactions_01032021.txt`. В этом режиме не нужны
новые файлы терминалов и blacklist; справочники не изменяются. Для каждой
операции обязана существовать единственная историческая цепочка карта → счёт
→ клиент и версия терминала на момент операции. Иначе пакет отклоняется.
Пересчитываются отчёты даты операций и следующего дня, чтобы учесть окна через
полночь. META_LOAD не получает ложную отметку о полной загрузке дня.
Одинаковое содержимое файла повторно не применяется; одинаковые операции с
одним ID объединяются, конфликтующие данные с одним ID останавливают пакет.
Для будущего дня сначала нужна обычная загрузка.

При необходимости доступны `--data-dir` и `--archive-dir`. Для продолжения
архивирования нужно указывать те же каталоги, что при исходной загрузке.

## Атомарность и восстановление

Одна транзакция PostgreSQL включает все изменения одного дня: STG,
инкременты, DWH, витрину, META_LOAD и журнал входных файлов META_FILES.
Очистка STG и вставка pandas используют одно физическое подключение.
При ошибке весь день откатывается, запуск завершается с кодом 1,
следующий день не начинается. Ранее успешно обработанные дни сохраняются.
До начала дня проверяется наличие всех обязательных файлов, внутри транзакции
проверяются столбцы, обязательные значения, ключи и дата операций.
Корректный полный снимок терминалов может быть пустым: это означает удаление
всех активных терминалов. Ограничений по доле удалений нет. Пустая таблица
с нужными столбцами отличается от повреждённого или отсутствующего файла.
Необязательные атрибуты могут содержать NULL; ключи и ссылки проверяются.

Архивирование происходит после commit. При сбое следующий запуск продолжает
перенос по журналу без повторной загрузки в DWH. SHA-256 позволяет проверить
содержимое входного файла и архива; файл с другим содержимым не перезаписывается.
Имена обычных архивов точно соответствуют заданию: `имя_файла.backup`.
Дополнительные пакеты сохраняются в `archive/late/<sha256>/имя_файла.backup`.

Блокировка PostgreSQL запрещает параллельный запуск ETL и подготовки bank
в одной базе. Она действует между транзакциями дней и во время архивирования.

## Дополнительные возможности и история

Атомарность, защита от параллельных запусков, восстановление архива и режим
поздних транзакций — согласованные улучшения. ТЗ разрешает более устойчивую
обработку файлов. Эти возможности не требуют дополнительных входных файлов
или контрольных манифестов для обычной загрузки трёх дней.

### История и ограничения

Карты, счета и клиенты версионируются по `coalesce(update_dt, create_dt)` источника.
Старая версия закрывается за микросекунду до начала новой; BETWEEN остаётся
включительным, как в учебных материалах. Удаление датируется выгрузкой, потому
что даты удаления в bank нет. Возврат записи закрывает версию удаления.
Проверяются допустимость и отсутствие пересечений интервалов.
Изменения справочников, затрагивающие уже рассчитанные дни, требуют отдельной
пересборки истории и автоматически не применяются. Текущий снимок bank не
позволяет восстановить неизвестные прошлые версии.

Справочники bank считываются один раз за запуск внутри первого нового дня.
Для равного времени операции упорядочиваются дополнительно по числовому ID.
Это согласованное правило стабильности, а не восстановление неизвестного
фактического порядка внутри секунды.

Миграции находятся в `sql_scripts/migrations`, их применение регистрируется
в META_SCHEMA_MIGRATIONS. Если существующие данные нарушают новые ограничения,
миграция останавливается без автоматического удаления/исправления строк.
В старых отчётах первоначальная дата report_dt сохраняется до пересчёта:
неизвестное время их построения не подменяется текущим временем.
Журнал файлов обеспечивает восстановление новых загрузок; для загрузок,
выполненных старой версией программы без журнала, автоматическое восстановление
архива не гарантируется.

По ТЗ каждый файл терминалов считается полным срезом. Программа не вводит
дополнительных порогов числа строк или доли удалений. Проверки структуры и
ключей не доказывают полноту выгрузки, но не заменяют это условие задания
произвольным бизнес-правилом.

## Проверки

Интеграционные тесты создают отдельную базу `etl_atomic_test_<uuid>` и удаляют
только её после завершения. Нужны PostgreSQL и право создания баз:

```bash
ETL_INTEGRATION_TESTS=1 .venv/bin/python -m unittest discover -s tests -v
```

Проверяются атомарность, ошибки PostgreSQL, сохранность STG и прошлых дней,
дубли и конфликты ID, интервалы истории, удаление и возврат, ограничения входа,
параллельный запуск, восстановление архива, поздние операции и окна через полночь,
срабатывания и контрпримеры правил фрода.
